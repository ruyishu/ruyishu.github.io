# 摘要

循环 Transformer（loop / recursive transformer）的核心主张很朴素：**不让层数变多，而是让同一组层多跑几遍**，用计算换有效深度。它听起来很美，但"到底值不值"必须落到严格对照上才算数。

我用 MiniMind（63.91M 参数、8 层、GQA 8Q-4KV、RoPE + YaRN、SwiGLU）做了一次严格 A/B：**同架构、同参数量、同数据、同超参、同步数，唯一变量是循环轮数 `n_loops`（T=1 → T=4）**，两条链路各自完整跑完 预训练 → SFT → DPO → RLAIF(GRPO) → Agentic RL，并在同一套评测口径下对比。

三条结论：

1. **训练侧稳定更低**：完整数据档上，预训练末态 loss **1.6433 → 1.5898（−3.3%）**，SFT 末态 loss **1.4955 → 1.3895（−7.1%）**。
2. **下游唯一有区分度的任务上，优势在四个阶段都成立**：20 题数学 ToolUse 通过率，T=1 完整档是 7/20，T=4 完整档在 SFT / DPO / GRPO / Agentic RL 四个阶段**全部 13/20**（+30 个百分点）。
3. **代价明确**：每步墙钟约 **3.5 倍**；到了 RL 阶段，循环带来的激活显存让"和 T=1 完全相同的 batch / 采样配置"直接 OOM，只能降到更小的配置才跑得动。

同时必须说清：这代 64M 规模的模型在 CEval / ARC / GSM8K 这类知识型基准上**全部贴着地板与随机水平**，测不出有效信号；唯一能分辨优劣的是"结构化输出 + 工具调用"这类任务。所以本文的结论只在这条口径上成立。

# 一、为什么必须做"严格 A/B"

循环结构最容易踩的坑是**把对比做糊**：如果拿"循环 4 遍的 8 层"去比"32 层"，那变量就不止一个——参数量的变化会混进来，结论就没法归因。

所以这里刻意把变量锁死到只剩一个：

- **唯一主动变量**：`n_loops`（1 → 4）。
- **参数完全一致**：63.91M，两条链路同架构、同配置，改动只落在 `model/model_minimind.py` 里约 30 行的循环分支与门控。
- **数据完全一致**：同一份预训练 / SFT / DPO / 偏好数据，同一条数集切分。
- **超参完全一致**：同样的学习率计划、同样的 batch、同样的步数。
- **工程隔离**：两个仓库目录、两套日志、两套产物，不使用符号链接，避免"共享文件被悄悄改动"。

# 二、实验设计

| 项 | 设置 |
|---|---|
| 模型 | MiniMind，63.91M，8 层，d_model 768，GQA 8Q-4KV，head_dim 96，RoPE(θ=1e6)+YaRN，SwiGLU，QK-Norm，词表 6400 |
| 唯一变量 | `n_loops` = 1（对照） / 4（实验） |
| 数据规模 | 两档：**mini（1/8 数据）** 与 **完整（14G 全量）** |
| 流程 | pretrain → SFT → DPO → RLAIF(GRPO) → Agentic RL → 评测 |
| 硬件 | 单卡 NVIDIA L20 48G，两条链路分别占一台机器 |
| 评测 | 自研：20 题数学 ToolUse（三层指标）+ CEval / ARC / GSM8K |

循环实现上的两个细节值得一提：**每一轮前向都把输入重新注入**，避免循环退化成对同一表征的反复变换；**门控（LayerScale 风格）初始化为 1/√T**，让训练起始时每轮贡献被温和缩放，而不是一上来就放大 4 倍。

# 三、训练侧结果

完整数据档（14G）的末态：

| 阶段 | 步数 | T=1（对照） | T=4（循环） | 相对变化 |
|---|---|---|---|---|
| 预训练 | 264,651 | 1.6433 | **1.5898** | **−3.3%** |
| SFT | 319,340 | 1.4955 | **1.3895** | **−7.1%** |

mini 档（1/8 数据）方向一致，SFT 的差距更明显（0.8854 → 0.7929，−10.4%）。

DPO 的 loss 不能这样横向比：DPO 的 loss 是相对参考策略的比值型目标，两条链路策略不同，数值本身不构成质量证据——这里只列出来备查（0.3107 vs 0.4678）。

# 四、下游结果：唯一能分辨优劣的地方

把上面这些权重放到同一个评测里：**20 道固定数学题 + 标准答案自动校验**，模型只拿到一个 `calculate_math` 工具，指标分三层——是否真的调了工具、表达式是否正确、最终答案是否正确。

| 阶段 | T=1 · mini | T=4 · mini | T=1 · 完整 | **T=4 · 完整** |
|---|---|---|---|---|
| pretrain | 0/20 | 0/20 | 0/20 | 0/20 |
| full_sft | 6/20 | 10/20 | 7/20 | **13/20** |
| dpo | — | 10/20 | 7/20 | **13/20** |
| grpo | 6/20 | 10/20 | 7/20 | **13/20** |
| agent | 6/20 | 10/20 | 6/20 | **13/20** |

几点值得注意：

- **T=4 在四个阶段全部是 13/20**，T=1 在 6~7/20。四个配对（同阶段、同数据、同评测）**全部是 T=4 胜**，最小配对差也是 +6 题。
- 差距不在"会不会调工具"上：两边的工具调用率几乎都是 20/20。差距落在**表达式正确率**上（例如完整档 SFT：8/20 → 14/20）。也就是说 T=4 的收益体现在"把题面正确翻译成算式"这一步。
- 空着的格子（T=1 mini 的 dpo）是当时没跑该权重，不是跑崩了。
- 换个工具集（再多给两个工具）时结论方向一致，但绝对分数会整体下移——这代模型对工具集规模很敏感，所以任何对比都必须写清工具集。

# 五、必须承认：知识型基准测不出东西

给同一批权重做 CEval（1,341 题，52 学科，5-shot 似然打分 + 域条件 PMI 校正字母先验）、ARC（5-shot）、GSM8K（few-shot 贪心生成）：

| 基准 | T=1 | T=4 | 随机水平 |
|---|---|---|---|
| CEval val | 23.5% ~ 26.5% | 23.8% | 25% |
| ARC-Challenge | 22.7% ~ 24.5% | 22.7% | 25% |
| ARC-Easy | 25.0% ~ 25.1% | 25.1% | 25% |

更直接的证据：**ARC 上多个不同权重的正确答案数完全相同**（都是 266/1172）——这是"恒定输出某个选项"的退化现象，说明这项基准在这代模型上不携带任何质量信息。GSM8K 同样是地板（few-shot 4/300；大样本档 1.52%）。

**结论**：这类规模下讨论"知识能力"没有意义；能测出差异的只有结构化输出与工具调用这类**格式与流程正确性**任务。任何只用知识型 MCQ 得出的"更强 / 更弱"结论，在这个量级上都应视为噪声。

# 六、代价：3.5 倍不是全部

| 维度 | 实测 |
|---|---|
| 每步墙钟 | **约 3.5 倍**（完整档 SFT：约 22h → 约 78h；预训练约 17h → 约 62h） |
| 显存（RL 阶段） | 和 T=1 完全相同的 batch / 采样配置**直接 OOM**：44.52 GiB 只剩 234 MiB |
| 结论 | 循环把"每步算 4 遍"的成本同时写到了时间与显存上；RL 阶段只能用小一档的 batch 与采样数 |

第三条尤其重要：这意味着**在单卡上，T=4 无法与 T=1 使用完全相同的 RL 超参**。我实测过对齐配置（batch 2 / num_generations 4），90 秒就 OOM，只能回退到 batch 1 / num_generations 2。因此 RL 两个阶段的对比是"**等数据覆盖、不等超参**"的对照，而 SFT 与 DPO 是不受影响的干净对照。

# 七、口径与局限（诚实清单）

1. **评测分辨率低**：20 题、1 题 = 5 个百分点。+6 题（+30pp）在方向上很一致，但绝对幅度的置信区间很宽。
2. **四个阶段不是独立样本**：SFT → DPO → GRPO → Agentic RL 是同一条血统的连续演化，四个"全胜"不等于四次独立验证。
3. **RL 段口径不对称**：T=1 的 RLAIF / Agentic RL 跑满了各自预算，T=4 侧因为显存与中断原因跑的是部分预算（RLAIF 约 36%，Agentic RL 目前是 2,412 / 39,988 步的快照），且超参小一档。我正在用 checkpoint 续跑把预算补齐，补齐后本文会更新。
4. **评测器自研**：不是 lm-eval-harness，因此**绝对值无法与论文或官方仓库的数字直接比较**，只有内部 A/B 的**相对**结论有效。
5. **单种子**：没有做多种子重复。
6. **参数量小**：63.91M 的结论不能外推到更大规模——这也是我把后续计划放在"更大 base + 更大题目集"上的原因。

# 八、复现

实验代码、唯一改动点、评测脚本与图表都在公开仓库：

- 仓库：<https://github.com/ruyishu/loopllm>
- 改动点：`model/model_minimind.py`（循环分支与门控，约 30 行）
- 训练脚本：`trainer/*`，全部带 `--n_loops`
- 评测脚本：`scripts/eval_math_toolcall.py`（自研的三层工具调用评测）
- 声明：`NOTICE` 里写明了基于 Apache-2.0 的改动范围与上游 MiniMind 的署名

复现时唯一要记住的一句话：**把变量锁到只剩 `n_loops`，否则一切对比都不成立。**

# 九、下一步

- **把题目量从 20 扩到 300~500**：这是当前性价比最高的一步，能把 5 个百分点级的分辨率压到 2~3 个百分点。
- **`n_loops` 扫描**：T=1 / 2 / 4 / 8，看收益是否随轮数单调、以及拐点在哪。
- **等预算对照**：给两条链路相同的墙钟或相同样本数，再比最终权重；同时把 T=4 的 RL 预算补齐。
- **更大 base**：把同样的 A/B 搬到 100M 以上的模型上，验证结论是否随规模保持。
- 换一批**有区分度**的任务（结构化输出、多步工具调用、格式约束）：知识型 MCQ 在这个量级不必再投算力。

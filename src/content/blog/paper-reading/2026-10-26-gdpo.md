## TL;DR

<strong>一句话：现在做多奖励 RL，大家默认"先把几个奖励加起来，再丢给 GRPO"。这篇说这个默认动作是错的——一加，不同的奖励组合就被压成同一个优势值，训练信号的分辨率直接掉一半。改法极简：<strong>每个奖励各自标准化，再相加，最后整体再标准化一次</strong>。</strong>

- <strong>最漂亮的一个反例（Fig 2）</strong>：两个二值奖励、两条 rollout。六个组合里，<strong>(0,1)、(0,2)、(1,2) 在 GRPO 下全都变成同一个优势 (−0.7071, +0.7071)</strong>。可"拿满两分"和"只拿一分"本该有强弱之分
- <strong>改法（Eq. 4–6）</strong>：<strong>逐奖励标准化 → 相加 → 批级再标准化一次</strong>。第二步保证奖励个数变多时数值尺度不炸
- <strong>结果一（工具调用，BFCL-v3，5 次平均）</strong>：Qwen2.5-1.5B 平均准确率 GRPO <strong>30.18</strong> → GDPO <strong>32.81</strong>，格式正确率 <strong>76.33 → 80.66</strong>
- <strong>结果二（数学）</strong>：DeepSeek-R1-1.5B 的 AIME <strong>GRPO 23.1 → GDPO 29.4（+6.3）</strong>，同时超长率 <strong>10.8% → 6.5%</strong>
- <strong>结果三（代码，三奖励）</strong>：DeepSeek-R1-7B 在 Apps 上 bug 率 <strong>20.3% → 18.8%</strong>，Codecontests bug 率 <strong>3.9% → 2.5%</strong>
- <strong>一个非常实用的工程结论</strong>：想让某个奖励优先，<strong>调权重基本没用</strong>（因为模型会先去刷容易的那个）；<strong>把容易的奖励"挂在"难奖励后面</strong>（难奖励达标才给分）才有效
- <strong>⚠️ 最该警惕的一点</strong>：论文全程只和 <strong>GRPO</strong> 比，<strong>不和"什么都不训的原模型"比</strong>。而 AIME 上三个底座全都<strong>低于原始分数</strong>（1.5B 29.8→29.4、7B 55.4→53.1、4B 63.7→56.9）
- <strong>✅ 仓库</strong>：github.com/NVlabs/GDPO，<strong>513 star</strong>，Apache-2.0（⚠️ 但 README 的 Licenses 段落写的是 NVIDIA Source Code License-NC，两处矛盾），<strong>verl / TRL / NeMo RL 三套实现</strong>，无 slurm，<strong>8×A100 约 1 小时</strong>（单卡约 2.5 小时）
- <strong>⚠️ 没放权重、没放数据</strong>；底座最大只到 7B
- <strong>⚠️ 没有独立 Limitations 章节</strong>，照实写
- <strong>主题</strong>：<strong>RL / 后训练</strong>（本周第 1 篇）。选它的理由：NVIDIA 主力组、算力门槛低、已被 TRL/verl/NeMo RL 集成，<strong>是能直接在上面接着做的那类 baseline</strong>

## 一、先看例子（大白话：三个都考 1 分的人，系统分不出差别）

> 💡 <strong>铺垫</strong>：假设你给模型定了两条规矩——「<strong>答对</strong>」得 1 分，「<strong>格式写对</strong>」得 1 分。然后让模型对同一道题答两次，按这两次谁好谁坏，去调整它。
>
> <strong>问题就出在"谁好谁坏"怎么算。</strong>

![论文 Figure 2：两条 rollout、两个二值奖励。左边 GRPO 把 (0,2)、(1,2)、(2,2) 压成只剩 2 个不同的优势值；右边 GDPO 逐奖励标准化后有 3 个](/images/paper-reading/2026-10-26-gdpo/2026-10-26-d65-1.webp)

<strong>具体看这一组</strong>（论文原文数）：

| 两条 rollout 的总分 | GRPO 给的优势 | GDPO 给的优势 |
|-|-|-|
| (0, 1) | (−0.7071, +0.7071) | (−0.7071, +0.7071) |
| (0, 2) | <strong>(−0.7071, +0.7071)</strong> | <strong>(−1.4142, +1.4142)</strong> |
| (2, 2) | (0, 0) | (0, 0) |

<strong>看清楚第二行</strong>：一条答错、另一条<strong>两分全拿</strong>，和"一条答错、另一条只拿一分"，<strong>GRPO 给的学习信号一模一样</strong>。

但这两件事的差距明明不一样：

- <strong>(0,1)</strong> = 你答对了但格式错了
- <strong>(0,2)</strong> = 你又答对又格式对

<strong>后者显然更该被强化。</strong>可 GRPO 看不出来。

> <strong>打个比方：你给三个学生打分，一个 60、一个 80、一个 100。</strong>
>
> <strong>GRPO 的做法是先把三个人各自的"语文 + 数学"加起来，再整体算名次。</strong>
>
> <strong>问题是：总分相同的人，可能是"语文 100 数学 60"，也可能是"语文 60 数学 100"——这两个人该被同样对待吗？</strong>
>
> <strong>GDPO 的做法是：先按单科排名，再合并。这样"两科都好"和"一科好一科差"就分得开了。</strong>

## 二、动机：多奖励已经是标配，但没人检查过 GRPO 还合不合适

现在的 RL 后训练早就不只优化"答对"了。常见的多奖励组合：

- <strong>准确率</strong> + <strong>格式</strong>（工具调用：格式不对整条作废）
- <strong>准确率</strong> + <strong>别啰嗦</strong>（数学：答案对，但别写八千字）
- <strong>通过率</strong> + <strong>别啰嗦</strong> + <strong>别写 bug</strong>（代码）

<strong>论文的原话是：大家把精力都花在"设计奖励"上，却默认 GRPO 拿来就能用。</strong>

<strong>而 GRPO 的优势公式是这样的</strong>：

<strong>A = (总奖励 − 组均值) / 组标准差</strong>，其中<strong>总奖励 = r₁ + r₂ + … + rₙ</strong>。

<strong>病根就在这个"先加"上</strong>：加法把多维信息压成一维，<strong>再标准化就把不同组合压成同一档</strong>。

<strong>后果不是"效果差一点"，而是三种</strong>：

1. <strong>信号分辨率下降</strong> —— 该区分的不区分
2. <strong>收敛变慢</strong> —— 策略更新方向不准
3. <strong>训练崩掉</strong> —— 论文在数学任务上真的看到了：<strong>约 400 步后 GRPO 的正确率开始往下掉，批内最大响应长度反弹到 8000</strong>

## 三、方法：把"先加后标准化"改成"先标准化后加，再整体标准化一次"

![论文 Figure 1：(a) GDPO 的两步——先逐奖励解耦标准化，再批级标准化稳住数值范围；(b) 工具调用任务上，GDPO 的正确率奖励爬升更快、平台更高](/images/paper-reading/2026-10-26-gdpo/2026-10-26-d65-2.webp)

### 3.1 三步公式

<strong>第一步：每个奖励各算各的</strong>

<strong>A\_j^(i) = (r\_j^(i) − 该奖励在本组内的均值) / 该奖励在本组内的标准差</strong>

注意这里是<strong>对每个奖励单独做组内标准化</strong>，不是对总和做。

<strong>第二步：把标准化后的优势加起来</strong>

<strong>A\_sum = A₁ + A₂ + … + Aₙ</strong>

<strong>第三步：在整批上再标准化一次</strong>

<strong>Â\_sum = (A\_sum − 整批均值) / (整批标准差 + ε)</strong>

<strong>为什么非要第三步？</strong>因为奖励个数一多，第二步加出来的数值尺度会跟着变大。<strong>不做这一步会怎样</strong>——论文在附录里说得很直接：<strong>偶尔会直接训崩</strong>。

### 3.2 效果有多大：看"不同优势值有几个"

![论文 Figure 3：横轴是 rollout 数或奖励数，纵轴是「能产生多少种不同的优势值」。GDPO（绿）明显高于 GRPO（灰）和去掉标准差的 GRPO（蓝），且差距随规模拉大](/images/paper-reading/2026-10-26-gdpo/2026-10-26-d65-3.webp)

这个指标很聪明——<strong>不看训练曲线，直接数"信号有多少档"</strong>。

- <strong>奖励数增加</strong>：GRPO 几乎不涨（多个奖励没带来更多区分度），GDPO <strong>呈指数级上升</strong>
- <strong>rollout 数增加</strong>：GRPO 线性慢涨，GDPO 明显更陡
- <strong>去掉标准差的 GRPO（Dr.GRPO / DeepSeek-v3.2 的做法）</strong>：比原版好一点，但<strong>远不如 GDPO</strong>

<strong>这一节顺带否掉了一个流行做法</strong>：有人说"去掉标准差归一化就能缓解难度偏置"——论文承认它能缓解一点点，<strong>但换成实验一看，收敛和下游表现都没变好</strong>。

### 3.3 一个更实用的发现：调权重没用，得改奖励结构

你想让模型优先保证"答对"、少管"别啰嗦"。直觉做法是<strong>把长度奖励的权重调小</strong>。

<strong>论文的结论是：基本没用。</strong>把长度权重从 1.0 降到 0.75、0.5，<strong>超长率只变 0.2–1.3 个百分点</strong>，而且降权之后也不一定更宽松——<strong>因为模型会先去刷那个容易的奖励，跟你给的权重关系不大</strong>。

<strong>真正管用的是"条件化"</strong>：

<strong>r\_容易 = 如果 r\_难 ≥ 阈值 t 则保留，否则记 0</strong>

也就是<strong>"答对了才谈格式分"</strong>。这样模型想拿格式分，<strong>必须先答对</strong>，顺序被硬编码进奖励里。

## 四、实验

### 4.1 工具调用（两个奖励：格式 + 正确）

| Qwen2.5-Instruct-1.5B | 平均准确率 | 格式正确率 |
|-|-|-|
| 原始模型 | 17.88 | 4.74 |
| GRPO | 30.18 | 76.33 |
| <strong>GDPO</strong> | <strong>32.81</strong> | <strong>80.66</strong> |

3B 上同样成立：<strong>39.20 → 40.87</strong>（准确率）、<strong>81.64 → 82.23</strong>（格式）。

<strong>但这里要注意</strong>：两者的绝对差不大（+2.6 / +2.0 分），而且<strong>5 次运行的方差没给区间</strong>。<strong>这一组更像是"稳一点"，不是"强一截"。</strong>

### 4.2 数学（两个互相打架的奖励：答对 + 别啰嗦）

![论文 Figure 5：DeepSeek-R1-1.5B。左图正确率——约 400 步后 GRPO（灰）开始掉，GDPO（绿）继续涨；中图长度奖励两者都很快打满；右图批内最大长度——GRPO 在 400 步后反弹到 8000，GDPO 继续下降](/images/paper-reading/2026-10-26-gdpo/2026-10-26-d65-4.webp)

<strong>这张图是全篇最有说服力的</strong>：它不只是"GDPO 分数高一点"，而是<strong>GRPO 在某个点之后开始倒退，GDPO 没有</strong>。

| AIME 准确率 | 原始 | GRPO | GDPO |
|-|-|-|-|
| DeepSeek-R1-1.5B | 29.8 | <strong>23.1</strong> | <strong>29.4</strong> |
| DeepSeek-R1-7B | 55.4 | <strong>50.2</strong> | <strong>53.1</strong> |
| Qwen3-4B-Instruct | 63.7 | <strong>54.6</strong> | <strong>56.9</strong> |

<strong>⚠️ 请把"原始"那一列也读一遍。</strong>三个底座上，<strong>加了长度约束之后，AIME 全都比不训还低</strong>——GDPO 只是<strong>掉得少</strong>。

<strong>真正的大头在"超长率"</strong>：

| AIME 超长率（越低越好） | 原始 | GRPO | GDPO |
|-|-|-|-|
| DeepSeek-R1-1.5B | 91.5% | 10.8% | <strong>6.5%</strong> |
| DeepSeek-R1-7B | 85.6% | 2.1% | <strong>0.2%</strong> |
| Qwen3-4B-Instruct | 71.3% | 2.5% | <strong>0.1%</strong> |

<strong>所以这篇的真实卖点应该这样表述</strong>：<strong>它让"压缩长度"这件事的代价更小</strong>——同样把 85.6% 的超长压到接近 0，GDPO 只损失 2.3 分准确率，GRPO 损失 5.2 分。

### 4.3 代码（三个奖励：通过率 + 别啰嗦 + 别写 bug）

| DeepSeek-R1-7B | 通过率 | 超长率 | bug 率 |
|-|-|-|-|
| 原始 | 28.1 | 73.9 | 32.9 |
| GRPO（三奖励） | 68.1 | 11.2 | 20.3 |
| <strong>GDPO（三奖励）</strong> | <strong>67.8</strong> | <strong>8.5</strong> | <strong>18.8</strong> |

<strong>Codecontests 上差距更清楚</strong>：bug 率 <strong>3.9 → 2.5</strong>、超长率 <strong>19.3 → 15.8</strong>，通过率持平（65.6 / 65.6）。

<strong>这组的读法是</strong>：<strong>不牺牲通过率的前提下，约束项做得更好</strong>。这正是多奖励最该有的样子。

## 五、Limitations

### 论文自述的：没有

⚠️ <strong>本篇没有独立的 Limitations 章节</strong>——正文到 Conclusion 之后直接进入附录。<strong>照实写，不硬凑。</strong>

### 我读出的 6 条

1. <strong>⭐ 只和 GRPO 比，不和"不训"比，这是全文最大的口径问题</strong>：AIME 上三个底座的 GDPO 结果<strong>全部低于原始模型</strong>（29.8→29.4、55.4→53.1、63.7→56.9）。<strong>"比 GRPO 好" 和 "比不做 RL 好" 是两个命题</strong>，论文只回答了前者，但标题与摘要读起来像后者
2. <strong>没有独立 Limitations 章节</strong>：最大的局限（只到 7B、只在三类任务、只和一个基线比）全靠读者自己推
3. <strong>工具调用那组增益太小、区间不明</strong>：+2.6 分准确率、5 次运行平均但<strong>没给标准差或置信区间</strong>；而格式正确率从 76 → 80 更像是"少犯格式错"而不是"更会调用工具"
4. <strong>"优势值档数变多" 是个代理指标，没有因果证明</strong>：它证明了"信号更细"，<strong>但没证明"更细就一定更好"</strong>。严格的做法应该造一个"档数相同但分布不同"的对照——论文没做
5. <strong>规模只到 7B，且数学任务全是 R1 蒸馏模型</strong>：DeepSeek-R1-1.5B/7B 本身就是长 CoT 模型，"压长度"对它们来说是特殊场景，<strong>换到 base 模型上结论是否成立未知</strong>
6. <strong>LICENSE 自相矛盾、且可能是非商用</strong>：仓库徽章 Apache-2.0，README 写 NVIDIA Source Code License-NC。<strong>要用在企业里，必须先核这个</strong>

| <strong>GiGPO / GraphGPO / SDPO</strong> | 改<strong>信用分配</strong>：步级、图级、稠密反馈 | <strong>同一族问题的另一维度</strong>：它们解决"<strong>一长串动作该给谁记功</strong>"，GDPO 解决"<strong>多个奖励该怎么合</strong>"。两者正交 |
| <strong>POLIA</strong>（10/5） | 改<strong>信号来源</strong>：给每个视觉对象单独发优势 | <strong>思路同源</strong>：POLIA 是"把优势在<strong>空间上</strong>拆开"，GDPO 是"在<strong>奖励维度上</strong>拆开"。<strong>两个拆分可以叠：先按对象拆，再按奖励拆</strong> |
| <strong>CapCurriculum</strong>（9/25、10/22） | 改<strong>数据顺序</strong>：按能力排课 | 都用多奖励（CapCurriculum 是答案 + 格式），<strong>本篇正好补上它没讨论的那一层——多个奖励怎么归一化</strong> |
| <strong>π-Distill</strong>（10/13） | 改<strong>监督来源</strong>：用教师替代奖励 | OPD 与 RL 的分野：OPD 的"奖励"是逐 token 的 KL（天然多维），<strong>GDPO 的洞察其实能反过来提示 OPD：多路信号相加前要不要各自标准化</strong> |

<strong>一句话串起来</strong>：这一周从"RL 的哪个零件最松"切入——<strong>DoF 拧探索、EAPO 拧奖励、GDPO 拧归一化</strong>，三个都是"改一行、效果可见"的小改动，<strong>也都适合直接拿来做 baseline</strong>。

## 七、启发与待跟进

1. <strong>⭐ 最可落地的一句话</strong>：<strong>多奖励时，别先 sum 再 normalize。</strong>回去翻自己的训练代码，只要看到 <strong>total = sum(rewards) → (total − mean) / std</strong>，就是中招了。改成"逐项标准化 → 相加 → 批级再标准化"，<strong>改动不到 10 行</strong>
2. <strong>⭐ "调权重没用，要条件化"是这次最值钱的工程经验</strong>：模型永远先去刷容易的奖励。<strong>想让某项目标优先，别调权重，把它做成"别的前提条件"</strong>。这条对所有 RLHF 流水线都成立
3. <strong>做 baseline 的成本极低</strong>：verl / TRL / NeMo RL 三套现成实现，<strong>8×A100 一小时</strong>。想验证"我的多奖励设置是不是也中招"，今晚就能跑
4. <strong>⚠️ 读这类"比 SOTA 好"的论文，先找"和原始模型比"那一列</strong>。这篇的 AIME 数据如果只看得分表会以为全线提升，<strong>加上"原始"那列就变成"少掉一点"</strong>
5. <strong>待跟进</strong>：① 在自己的多奖励设置里复现 Fig 2 的坍缩（<strong>最便宜的验证</strong>：只算优势，不训练）② 把 GDPO 与 POLIA 式的"对象级优势"叠加 ③ 检查 7B 以上是否仍成立 ④ 若能拿到权重，验证 LICENSE 的实际约束

## 八、结论

<strong>这是一篇"改一行、思路清楚"的论文</strong>：它没有提出新模型、新数据、新奖励，只是指出<strong>"多奖励 RL 里先加后标准化"这个人人都在做的动作会丢信息</strong>，然后给了个几乎零成本的正法。

<strong>它的证据强度要打折</strong>：只和 GRPO 比、只到 7B、增益小且无区间。<strong>但它作为 baseline 的价值很高</strong>——代码全开源、三套框架、一小时能跑完。

<strong>今日一句</strong>：<strong>多个指标相加之前，先各自归一化——不然你以为在给模型更丰富的信息，其实是在把它压成一个数。</strong>
